# ForgeCrew — 요구사항

## 목표와 사용 환경

ForgeCrew는 수십 명 규모의 부서에서 GitHub 대화를 통해 동료 PC의 AI 자동화를 이용하는 시스템이다. 사용자는 GitHub에서 질문·조사·구현·리뷰를 요청하고, Worker는 자신의 기존 개발 환경으로 이를 수행한다.

- GitHub Enterprise Server의 허용된 저장소에서 Issue와 PR을 독립적인 지속 대화 세션으로 사용한다.
- 단일 Dispatcher가 REST 폴링으로 입력을 수집하고 여러 Worker에 분배한다.
- Dispatcher는 PAT를 사용한다. Worker는 로그인된 `gh` CLI와 로컬 Codex/Claude 구독 로그인을 사용한다.
- Worker 하나는 여러 세션을 병렬 실행하며, Windows와 Linux에서 동작한다.
- 사용자 인터페이스는 GitHub다. 설치 이후 Worker의 재연결·업데이트·재시작은 자동으로 처리한다.
- 공통 설정·AI 지침·출처 표기는 Dispatcher의 단일 YAML로 관리한다. 지원되는 설정 변경에는 Worker 패키지 재배포가 필요하지 않다.

## 핵심 사용 흐름

| 상황 | 흐름 | 관련 요구 |
|---|---|---|
| Issue/PR에서 요청 | 활성화·모델·effort 라벨 지정 → 본문으로 최초 실행 → 동료 계정의 답변 → 일반 댓글로 후속 대화 | F1, F2, F6, F10 |
| 실행 중 추가 입력 | 일반 댓글은 FIFO 대기, `/ai steer`는 현재 실행에 추가 지시, `/ai stop`은 현재 실행 중단 | F3 |
| AI의 질문 | 질문을 GitHub에 남기고 현재 실행을 마침 → 슬롯 반환 → 이후 댓글을 다음 입력으로 처리 | F3, F5 |
| 다른 Worker에서 이어가기 | 이전 실행의 소유권 회수 → GitHub 대화·원격 Git 상태 확인 → 새 실행에서 미완료 작업 재개 | F4, F7 |
| Worker 새 버전 배포 | 사내 npm 게시 → 자동 설치 준비 → 실행 정리 → 교체·재시작 → 상태 재조정 | F11 |
| 공통 지침·표기 변경 | YAML 수정 → 전체 검증·활성화 → Worker 동기화 → 다음 Turn에 적용 | F9, F10, F12 |

## 범위와 완료 수준

첫 실사용 릴리스는 아래 **F1–F12, N1–N6 전체**를 충족한다. 개발 중 한 엔진·한 Worker로 먼저 검증할 수 있으나, 자동 업데이트·재연결·다중 Worker 복구를 선택 기능으로 미루지 않는다.

플랫폼은 Git 절차를 강제하지 않는다. 대상 저장소의 지침을 유지하고 실행 시 공통 맥락만 제공한다. Worker 사이의 로컬 미커밋 파일·Provider 내부 실행 상태 복제, 별도 대화 웹앱, 외부 큐·DB 서버, 전용 Runner는 제품 구성에 포함하지 않는다. 배포 관리 도구와 호스트·TLS 구성은 운영 환경의 책임이다.

## 용어

| 용어 | 의미 |
|---|---|
| Session | Issue 또는 PR 하나의 지속 대화. 유휴 상태도 유지된다. |
| Input | GitHub에서 수집한 최초 요청 또는 일반 댓글. |
| Turn | Input 하나를 처리하는 논리적 작업. |
| Attempt | 장애·조향 재개 등을 포함한 Turn의 실제 실행 시도. |
| Slot | Worker가 동시에 수행할 수 있는 활성 실행 자리. 유휴 Session은 차지하지 않는다. |
| Lease | Attempt의 실행 권한과 유효 기간. |

## 기능 요구사항

### F1. 저장소 허용 목록과 AI 활성화

**동작**

- 관리자가 지정한 저장소의 활성화 라벨이 붙은 Issue/PR만 실행 대상이다. 기본 이름은 `ai:enabled`이며 중앙 YAML에서 변경할 수 있다. 모델·effort·배정·상태 라벨만으로 활성화하지 않는다.
- 해당 저장소에 Write 이상 권한을 가진 사용자만 요청·실행 제어·AI 설정 변경을 할 수 있다. 읽기 권한 사용자의 글은 참고 맥락이며 실행 지시가 아니다.
- 최초 활성화는 본문을 한 번 실행한다. 과거 댓글은 맥락으로 읽으며, 과거 명령과 요청을 각각 새 작업으로 재생하지 않는다. 활성화 후 작성된 입력은 순서대로 수집한다.
- Write 이상 사용자가 활성화한 행위는 당시 본문을 실행 대상으로 지정한 것으로 취급한다. 활성화·설정 변경의 행위자는 GitHub 기록으로 확인한다.
- 활성화 라벨 제거는 신규 입력 접수와 다음 Turn 시작을 멈춘다. 진행 중 Turn은 마무리하고 대기열은 보존한다. 즉시 중단은 `/ai stop`으로 요청한다.
- 재활성화는 보존된 대기열을 이어간다. 본문을 다시 최초 실행하지 않으며 비활성 기간의 댓글은 맥락으로만 사용한다.
- Issue/PR의 close·reopen·merge 자체는 AI 활성화 여부를 바꾸지 않는다.

**수용 기준**

허용 범위·권한·라벨을 모두 만족해야 실행된다. 라벨 제거·재추가로 입력이 삭제되거나 과거 작업이 반복되지 않는다. 상태·배정 라벨만 남은 객체에서 실행이 시작되지 않는다.

### F2. Issue·PR 독립 지속 세션

**동작**

- 사내 GitHub 호스트·저장소·객체 종류·번호로 세션을 식별한다. PR이 Issues API에서도 나타나더라도 세션을 이중 생성하지 않는다.
- 같은 객체의 후속 입력은 같은 논리 세션에서 처리한다. Issue와 연결된 PR은 별도 세션과 대기열을 가진다.
- 관련 Issue/PR, diff, 브랜치, 원격 작업 결과는 필요에 따라 맥락으로 참조한다.
- 같은 Worker에서는 로컬 AI 세션과 작업 공간을 재사용한다. Worker 또는 실행 엔진이 달라지면 GitHub 기록과 확인 가능한 작업 결과로 맥락을 재구성한다.

**수용 기준**

후속 대화가 앞선 맥락을 사용한다. 연결된 Issue/PR의 입력·중단·설정은 서로 독립적으로 적용된다.

### F3. 일반 댓글 큐와 실행 제어 명령

**동작**

| 입력 | 동작 |
|---|---|
| 일반 댓글 | 같은 세션의 FIFO 입력으로 등록한다. 실행 중에는 다음 Turn을 기다린다. |
| `/ai steer <내용>` | 명령이 작성된 시점의 활성 실행에 지시를 반영한다. 해당 실행이 이미 끝났으면 적용하지 않았음을 알린다. |
| `/ai stop` | 대상 Turn을 중단하고 그 Turn은 자동 재시도하지 않는다. 기존 대기 입력은 보존하며 현재 실행의 종료가 확인되면 다음 입력을 처리한다. |

- 명령은 새 댓글의 첫 번째 비어 있지 않은 일반 텍스트 줄에서 인식한다. 인용문·코드 블록·과거 댓글 편집은 새 제어 명령이 아니다.
- 실행 중이 아닐 때의 stop/steer는 상태를 알려주는 것으로 끝난다. 다음 Turn에 뒤늦게 적용하지 않는다.
- steer의 직접 전달이 없는 엔진에서는 현재 실행을 안전하게 중단한 뒤 추가 지시를 포함해 같은 논리 작업을 이어간다. 이 사실을 표시하고 일반 큐의 뒤로 보내지 않는다.
- AI는 확인이 필요하면 질문을 최종 응답으로 남기고 현재 실행을 마친다. 이후 답변은 일반 댓글과 동일한 새 Turn이다.
- 런타임의 네이티브 질문 요청은 현재 Attempt의 수명 안에서 처리한다. 종료 시 요청을 정리하고, 실제로 사람의 응답을 기다려 막히는 경우에는 질문을 보존한 채 실행을 마무리한다. 가짜 답변을 생성하지 않는다.
- 전체 대기열의 진행도 멈추려면 활성화 라벨을 제거한다. 라벨이 제거된 상태라도 기존 실행에 대한 stop은 처리한다.

**수용 기준**

일반 댓글 두 개는 차례대로 처리된다. stop/steer가 일반 큐에 밀리지 않는다. 질문 후 아무도 답하지 않아도 슬롯을 영구 점유하지 않는다. 취소된 요청·오래된 제어 명령이 새 실행을 바꾸지 않는다.

### F4. 단일 Dispatcher와 분산 배정

**동작**

- Dispatcher는 입력·배정·실행 소유권의 기준 상태를 관리한다.
- Worker는 영속적인 고유 ID를 가지며 GitHub의 배정 표시에서 자기 세션을 확인할 수 있다. 실제 실행은 Dispatcher에서 권한을 받은 뒤 시작한다.
- 모델 라벨로 실행 가능한 엔진과 Worker를 내부에서 판단한다. Worker의 활성 엔진, 실제 모델·effort 지원, 저장소 접근, 사용량 제한, 가용 슬롯을 고려한다.
- 선택한 최신 모델을 실행할 Worker가 모두 바쁘면 대기한다. 편의를 위해 다른 계열·낮은 버전·낮은 effort로 조용히 바꾸지 않는다.
- 같은 세션은 하나의 Turn만 활성 실행한다. 가능한 경우 이전 Worker를 재사용하되 다른 적합한 Worker의 사용을 막지는 않는다.
- 배정·상태 표시는 플랫폼 전용 라벨로 관리하며 사람의 Assignees와 다른 라벨을 보존한다.

**수용 기준**

둘 이상의 Worker가 세션을 분산 실행한다. 용량·모델·접근 조건이 맞지 않으면 대기 이유가 드러난다. 경쟁 Claim에서 유효 실행 소유권은 하나만 발급된다.

### F5. Worker 다중 세션 실행과 격리

**동작**

- Worker의 `maxConcurrentSessions`는 활성 실행의 상한이다. 유휴 대화와 사람의 답변 대기는 슬롯을 차지하지 않는다.
- 세션별 작업 디렉터리, AI 실행, 임시 데이터, 로그를 분리한다. 한 세션의 중단·장애가 다른 세션을 종료하지 않는다.
- Git 작업 공간은 worktree 또는 독립 clone으로 준비한다. 동일 브랜치 점유 때문에 사용자의 정상 작업 흐름을 막지 않도록 한다.
- 사용자가 평소 쓰는 로컬 checkout을 임의로 작업 공간으로 사용하거나 정리하지 않는다. Worker가 관리하는 작업 공간에 한정한다.
- 로컬 파일 격리와 보안 Sandbox는 별개다. 실행 권한은 동료의 로컬 런타임·회사 정책을 따른다.

**수용 기준**

같은 저장소의 두 세션을 병렬 실행해도 파일·프로세스가 섞이지 않는다. 유휴 세션이 누적되어도 활성 실행 용량을 소모하지 않는다.

### F6. Codex·Claude 연동과 모델·effort 설정

**동작**

- Worker 설정에서 Codex, Claude, 또는 둘 다 활성화한다. 설치·인증·모델 상태는 엔진별로 진단한다.
- Codex는 구독 로그인된 로컬 App Server, Claude는 구독 로그인된 공식 Claude Code의 구조화된 프로그램 인터페이스로 연동한다.
- Issue와 PR은 동일한 라벨 체계를 사용한다. 아래는 기본 라벨 이름이며, 운영자는 중앙 YAML에서 이름·접두어를 설정할 수 있다.

| 설정 | 허용 값 |
|---|---|
| 모델 | `ai:model:sol`, `ai:model:terra`, `ai:model:opus`, `ai:model:sonnet` |
| effort | `ai:effort:low`, `ai:effort:medium`, `ai:effort:high`, `ai:effort:xhigh` |

- 모델 라벨은 계열명만 사용한다. 숫자 버전은 가용 모델 정보에서 숫자 구성 요소를 비교해 가장 높은 버전으로 해석한다.
- 설정 우선순위는 **세션 라벨 → 저장소 기본값 → 전체 기본값**이다. effort 기본값도 없으면 선택한 모델의 런타임 기본값을 사용한다. 전체 기본 모델은 Dispatcher 설정에서 지정한다.
- 같은 종류의 라벨이 복수이거나 값이 잘못되면 새 Turn을 보류하고 이유를 표시한다. 임의로 하나를 선택하지 않는다.
- 실행을 시작할 때 실제 모델 ID·effort를 고정해 기록한다. 라벨 변경과 더 높은 모델 버전 발견은 다음 Turn부터 적용한다.
- 모델·effort 또는 Auto Review가 실행 환경에서 지원되지 않으면 해당 조합을 실행하지 않고 원인을 드러낸다.

**수용 기준**

계열 라벨만으로 적절한 Worker가 선택되고 최신 가용 숫자 버전이 실행된다. 모델을 바꾸어도 Issue/PR 세션과 이력은 유지된다. 이미 진행 중인 Turn의 설정은 중간에 바뀌지 않는다.

### F7. Worker 장애 감지와 논리적 재개

**동작**

- Worker는 Dispatcher 통신 실패로 종료하지 않고 백오프를 적용해 재접속한다. 등록·Heartbeat·실행·게시 상태를 복구한다.
- 유효한 Lease 동안에는 단기 연결 실패만으로 AI 실행을 즉시 죽이지 않는다. Lease를 잃으면 해당 실행을 중단하고 Worker 자체는 유지한다.
- 재배정 시 이전 실행의 늦은 결과·게시 요청을 새 실행의 결과로 받아들이지 않는다.
- 장애 복구는 GitHub 대화, 원격 Git 상태, 이미 기록된 실행 결과를 이용한다. 다른 PC의 미커밋 파일이나 내부 AI 상태를 복원했다고 가정하지 않는다.
- 실행 재시도와 결과 전송·댓글 게시 재시도를 분리한다. 결과를 게시하지 못했다는 이유로 완료된 코드 작업을 반복하지 않는다.
- 같은 PC의 작업 파일과 실행 기록은 보존한다. 사용자가 취소한 Turn은 장애 복구 대상으로 자동 부활시키지 않는다.

**수용 기준**

Dispatcher 재배포, Worker 종료, 절전·복귀, 장기 단절 후 자동 재조정된다. 유효하지 않은 실행이 새 작업에 결과를 덮어쓰지 않는다. 외부 작업의 불확실성은 숨기지 않는다.

### F8. AI 도구 실행 요청의 Auto Review

**동작**

- 각 런타임의 AI 기반 자동 검토·승인 모드를 사용한다. 허용과 거절은 런타임 정책에 따라 판단한다.
- 사람의 업무상 의사결정을 묻는 질문은 자동 승인 대상이 아니다.
- 승인 거절·관리 정책 제한은 결과에 남긴다. 자동 검토를 사용할 수 없는 경우 무조건 허용 모드나 권한 확대 모드로 대체하지 않는다.
- 이 기능은 도구 실행 승인에 관한 것이다. GitHub PR 리뷰·병합 여부는 별도의 사용자 요청과 저장소 권한에 따라 AI가 판단한다.

**수용 기준**

도구 실행 승인에는 사람이 매번 개입하지 않는다. 실제 활성 모드와 거절 이유를 확인할 수 있다. 두 엔진에서 필수 자동 검토 경로가 검증된다.

### F9. 공통 AI 맥락과 자율적인 Git 작업

**동작**

- 공통 작업 지침은 중앙 YAML의 멀티라인 문자열로 관리하며 Worker가 Dispatcher에서 받아 사용한다. 실행별 세션·요청·관련 객체·작업 공간·실행 상태는 별도 구조화 맥락으로 전달한다.
- 새 Turn을 시작할 때 공통 지침의 revision을 고정한다. 설정 변경은 다음 Turn부터 적용하며, 기존 AI 세션을 재개할 때도 실제로 새 지침이 적용되어야 한다.
- 기존 저장소 지침, 사용자 환경, 인증·Git 서명 설정을 유지한다.
- 설명만 하거나, 파일을 수정하거나, 커밋·Push·PR을 만들지 여부는 AI가 판단한다. 런타임은 그 순서를 상태 전이의 필수조건으로 삼지 않는다.
- 원본 GitHub 대화에 게시할 응답은 Worker의 게시 경로를 이용한다. AI가 같은 최종 답변을 별도로 중복 게시하지 않도록 안내한다.

**수용 기준**

답변만 하는 요청도 정상 완료된다. Git 작업은 자율적으로 수행한다. 대상 저장소의 지침 파일은 유지된다. 공통 지침 변경 뒤 패키지 업데이트 없이 다음 Turn이 새 지침을 사용하고, 이전 Turn의 지침은 변하지 않는다.

### F10. GitHub 폴링과 동료 명의 결과 게시

**동작**

- Dispatcher는 저장소의 Issue/PR·라벨·일반 댓글·제출된 PR 리뷰와 라인 댓글을 폴링한다.
- 페이지 조회, 중복 제거, 영속 커서와 재조정으로 일시적 누락을 회수한다. 중단 중 새로 활성화된 세션도 발견한다.
- AI 답변·질문·진행·실패 댓글은 Worker의 `gh` 로그인으로 작성한다. Dispatcher PAT는 폴링과 배정·상태 라벨 관리에 사용한다.
- AI가 작성한 본문에는 작고 명확한 AI 작성 표기를 붙인다. Worker 게시기는 중앙 YAML의 `output.attribution`을 본문 끝에 한 번만 추가한다. 순수 런타임 상태 안내는 별도의 자동화 표기를 사용한다.
- 플랫폼 게시 경로의 댓글·리뷰는 런타임이 표기를 보장한다. AI가 직접 생성·편집하는 PR 본문 등의 콘텐츠에는 같은 표기를 공통 지침으로 전달하고, 확인 가능한 작성 결과에서 누락을 점검한다. 런타임이 관측하지 못하는 직접 쓰기까지 강제로 통제한다고 가정하지 않는다.
- 표시 문구와 보이지 않는 자동화 식별자는 별개다. 문구 변경·게시 재시도·동일 동료의 직접 작성 댓글이 자동 출력 식별을 깨뜨리지 않는다.
- 댓글 게시 전후 기록을 남겨 응답 유실·재시작에서 중복을 통제한다. 게시 결과가 불확실하면 기존 댓글을 먼저 확인한다.
- Worker가 없는 대기·설정 오류는 GitHub 상태 라벨과 Dispatcher 운영 정보로 드러낸다. 댓글을 쓰기 위해 다른 계정으로 몰래 대체하지 않는다.

**수용 기준**

답변 작성자는 실행·게시한 동료 계정이며, 플랫폼이 게시한 AI 콘텐츠에는 설정된 표기가 한 번 표시된다. 해당 동료의 직접 작성 댓글은 정상 입력으로 인식된다. 문구 변경·분할 게시·재시도에서 표기 중복이나 자기 응답 루프가 생기지 않는다. 직접 작성 경로의 보장 범위는 운영자에게 숨기지 않는다.

### F11. 간편한 설치와 무인 자동 업데이트

**동작**

- Worker는 사내 npm 패키지로 설치하며 PC의 Node.js를 사용한다. Git, 로그인된 `gh`, 활성화할 Codex/Claude는 로컬 환경을 사용한다.
- 초기 설정에서 연결·등록·엔진 선택·동시 실행 수를 설정하고 로컬 실행 환경을 진단한다.
- 사용자 로그인 시 백그라운드 시작한다. 터미널 창을 닫아도 계속 실행하며, 같은 Worker의 중복 기동을 막는다.
- 작은 Launcher가 버전별 ForgeCrew 프로세스를 실행한다. 업데이트 감지·설치 준비·Drain은 ForgeCrew 내부 기능이다.
- 새 릴리스는 실행 중 자동 감지·설치·적용·재시작한다. 활성 Turn을 마무리하거나 안전하게 중단해 이어가며, 새 Turn 시작은 잠시 멈춘다.
- 다운로드·설치 실패면 현재 버전을 유지한다. 새 버전의 로컬 기동 실패면 이전 정상 버전으로 복귀한다.
- Dispatcher 또는 npm 일시 불통은 정상 버전을 폐기할 이유가 아니다. 설정·Worker ID·작업 공간·미전달 결과는 버전 교체 후에도 유지한다.

**수용 기준**

Windows/Linux에서 초기 설정 이후 새 버전 게시만으로 자동 업데이트·재시작한다. 설치 중 강제 종료, 새 버전 오류, 네트워크 단절에서도 정상 버전 또는 재시도 경로가 남는다.

### F12. 중앙 설정 배포와 운영 정보

**동작**

- 공통 설정은 Dispatcher의 `config.yaml` 하나로 관리한다. 저장소·라벨·모델 기본값·운영 주기·업데이트 배포 정보·공통 AI 지침·게시물 표기를 포함한다. 프롬프트도 같은 YAML에 작성한다. 기본 스키마와 초기 값은 `config.example.yaml`을 기준으로 한다.
- PAT·등록 비밀값은 환경변수 또는 Secret 참조로 주입한다. Worker에는 인증된 설정 API를 통해 실행에 필요한 비밀 없는 항목만 제공한다.
- Worker 로컬 설정은 Dispatcher 주소·자기 인증, 활성 엔진, 동시 실행 수, 작업 경로·실행 파일 경로 등 PC 고유 환경이다. 중앙 설정이 동료의 로그인·엔진 선택·로컬 용량을 임의로 덮어쓰지 않는다.
- 설정을 다시 읽을 때 문법·스키마·값의 관계를 검증하고 전체가 유효한 경우에만 새 revision을 활성화한다. 잘못된 수정은 마지막 정상 설정을 유지하며 이유를 알린다.
- Worker는 시작·재접속·주기 확인 때 변경을 받아 로컬에 원자적으로 캐시한다. Dispatcher 불통·설정 다운로드 실패는 Worker 종료 사유가 아니다. 캐시는 새 실행 권한을 대신하지 않는다.
- 공통 지침·모델 기본값·표기는 다음 Turn부터 적용한다. 이미 발급한 Lease, 실행 중 Turn, 확정한 게시 본문은 해당 스냅샷을 유지한다. 재시작이 필요한 환경 설정은 적용 시점을 명확히 표시한다.
- 설정 스키마가 맞지 않는 Worker는 기존 유효 작업과 업데이트·재접속 경로를 유지하고, 이해하지 못하는 새 설정의 작업만 보류한다. 지원되지 않는 값을 조용히 버리지 않는다.
- Session·Input·Attempt·실제 모델·설정 revision·Worker·Delivery를 연결해 진단한다. 비밀값이나 전체 프롬프트를 일상 로그에 출력하지 않는다.
- 운영자가 바꿀 만한 정책·기본값·문구·지침·주기는 구조를 크게 바꾸지 않는 범위에서 설정으로 제공한다. 내부 상태 전이·인증 검증 등 정확성 계약은 임의 문자열 설정으로 대체하지 않는다.

**수용 기준**

단일 YAML 수정으로 여러 Worker의 다음 Turn에 새 지침·표기가 적용되고 Worker 패키지 업데이트를 요구하지 않는다. 잘못된 YAML, 설정 전송 실패, 캐시 손상, 신구 버전 혼재에서도 정상 설정·작업을 보존하고 문제를 진단할 수 있다. 서버 비밀값은 Worker 응답·캐시·로그에 포함되지 않는다.

## 비기능 요구사항

| ID | 요구 | 수용 기준 |
|---|---|---|
| N1 | 단일 Docker Dispatcher와 로컬 SQLite로 경량 운영한다. 배포 관리 도구와 분리한다. | 이미지·영속 데이터·설정만으로 구동하고 컨테이너 교체 후 상태가 유지된다. |
| N2 | Windows/Linux Worker의 핵심 코드를 공유한다. | 두 환경에서 실행·중단·업데이트를 시험하고 OS 처리는 좁은 어댑터로 제한한다. |
| N3 | 입력 유실·중복 소유권·불확실한 외부 결과를 구분해 복구한다. | 장애 주입 시험을 통과한다. Git Push 등 외부 부작용의 완벽한 exactly-once를 주장하지 않는다. |
| N4 | 저장소 Write 권한, 동료의 인증·회사 정책과 비밀정보 경계를 지킨다. | 권한 없는 입력을 실행하지 않고 토큰을 로그·댓글·중앙 설정에 복제하지 않는다. |
| N5 | 부서 규모에 맞는 설치와 무인 유지보수를 제공한다. | 릴리스마다 동료에게 종료·재설치·재시작을 요구하지 않으며, 지침·표기 변경은 중앙 설정만으로 반영된다. |
| N6 | 런타임 기능 차이를 명시된 대체 동작으로 처리한다. | stop·steer·질문·모델·Auto Review가 실제 계약대로 동작한다. 필수 기능을 단순 미지원 안내로 완료 처리하지 않는다. |

## 구현 시 입력할 환경값

사내 GitHub 호스트와 테스트 저장소, Dispatcher 주소·PAT, 사내 npm 주소·패키지 scope는 배포 시 제공한다. 설치된 런타임 버전과 관리 정책은 실제 동작 시험의 입력이다. 제품 동작 결정은 이 문서에 정의하며, 외부 환경값을 이유로 별도 설계가 계속 미정인 상태로 두지 않는다.
